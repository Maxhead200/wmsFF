# Контракт планшета v2 — опубликован PR343, 27.09.2026

Базовый адрес клиента: `https://wms.logoff.pro/api/v1/attendance-device/`.
Маршруты включены на нашей WMS. Не направлять запросы на административные Payroll API от имени сотрудника или с сохранённым паролем администратора.

## POST register

Вход: `{ "code": "одноразовый код", "name": "Планшет 01", "protocolVersion": 2 }`.

Ответ: `{ "protocolVersion": 2, "deviceId": "uuid", "warehouseId": "uuid", "warehouseName": "ФФ Москва", "token": "отзываемый токен" }`.

Код выдаётся администратором филиала/собственником в ФОТ, имеет срок жизни и ограничение числа попыток, используется один раз. Филиал определяется кодом на сервере. Токен устройства даёт только чтение минимальных карточек и регистрацию событий своего филиала. Переименование сохраняет deviceId. Повторную регистрацию с непустой очередью нельзя выполнять без согласованного переноса; клиент не содержит кнопки сброса данных.

## POST receipts

Авторизованный планшет подтверждает локальное сохранение принятых результатов: `{ "ids": ["UUID события"] }`. Только собственные события со статусом ACCEPTED помечаются прочитанными. REVIEW остаётся видимым до решения администратора. Повтор безопасен; отметки и смены не удаляются.

## GET state

Заголовок `Authorization: Bearer <token>`.

Ответ:

```json
{
  "protocolVersion": 2, "deviceId": "uuid", "warehouseId": "uuid", "serverTimeMs": 1790000000000,
  "employees": [{
    "id": "uuid", "name": "Сотрудник", "warehouseId": "uuid",
    "loader": false, "active": true, "distinguishing": "",
    "openSinceMs": null, "revision": 1
  }]
}
```

Карточки не содержат сумм, ставок и реквизитов. Монотонная revision меняется при изменении карточки или состояния смены, включая корректировки администратором. Полный список: отсутствующие карточки исключаются из кэша. Ответ не может содержать чужой филиал.

## POST events

`Authorization: Bearer <token>`, `Idempotency-Key: <eventId>`. JSON без изображения. Фото обязательно сохраняется локально при CLOCK_IN/CLOCK_OUT и хранится 35 дней, но его передача не является условием приёма отметки. Для HANDLING фото не требуется.

```json
{
  "protocolVersion": 2, "photoPolicy": "LOCAL_35_DAYS",
  "eventId": "uuid", "employeeId": "uuid", "deviceId": "uuid", "warehouseId": "uuid",
  "kind": "CLOCK_IN", "capturedAtMs": 1790000000000, "elapsedAtMs": 120000,
  "serverOffsetMs": 20, "lastSyncAtMs": 1789999990000,
  "photoSha256": "hex", "payload": {}
}
```

HANDLING payload: `{ "type": "UNLOADING", "startsAtMs": 1790000000000, "pallets": "1.25", "participantIds": ["uuid"], "comment": "" }`.
Количество передаётся десятичной строкой; не вычислять денежные суммы на планшете. Создатель включён в список. Помощники могут быть сборщиками; все участники активны в том же филиале. Работа требует подтверждения в ФОТ.

Ответ:

```json
{
  "eventId": "тот же uuid", "status": "ACCEPTED", "photoStored": false,
  "reason": "", "employee": {
    "id": "uuid", "name": "Сотрудник", "warehouseId": "uuid", "loader": false,
    "active": true, "distinguishing": "", "openSinceMs": 1790000000000, "revision": 2
  }
}
```

Для спорной отметки статус REVIEW и понятная причина; исходное событие сохраняется, локальное фото подчиняется сроку 35 дней. Для HANDLING employee может отсутствовать. ACCEPTED у HANDLING означает приём работы, не подтверждение начисления и не выплату.

Сервер обязан:

- транзакционно обеспечить уникальность eventId и хранить исходный результат; повтор после потери ответа не создаёт вторую смену/работу;
- проверять неизменность полезной нагрузки при повторе UUID;
- связать токен с устройством/филиалом и проверить сотрудника и участников;
- при отдельном запросе фото валидировать содержимое, длину и SHA256, хранить закрыто; не доверять расширению файла;
- принимать отметки без файла; photoStored не влияет на подтверждение отметки;
- блокировать конкурирующие изменения одного сотрудника; не создавать пересекающиеся интервалы с двух планшетов;
- хранить исходное время устройства, смещение и время получения, подозрительное время направлять на проверку;
- сохранять аудит источника, не задваивать импортированные/ручные интервалы и оплаченные дни;
- в REVIEW сохранять событие для разрешения администратором без создания лишних оплачиваемых интервалов.

## Фотографии по запросу

Администратор филиала/собственник явно запрашивает фото события через ФОТ. Сервер сохраняет аудит запроса. `GET state` возвращает не более 100 незавершённых запросов только данного устройства:
`"photoRequests": [{ "requestId": "uuid", "eventId": "uuid" }]`.

Планшет проверяет принадлежность исходного события устройству/филиалу и срок от момента съёмки с учётом смещения времени. Отсутствующий или повреждённый файл не заменяется новым снимком.

`POST photo-requests/:requestId`, Bearer token, `Idempotency-Key: requestId`, multipart:
- `requestId`, `eventId`;
- `status`: `AVAILABLE`, `EXPIRED` или `UNAVAILABLE`;
- только при `AVAILABLE` — `photo` JPEG до 4 МБ, соответствующий сохранённому SHA256.

Ответ: `{ "requestId": "uuid", "eventId": "uuid", "status": "STORED" }` после устойчивого сохранения, либо `EXPIRED`/`UNAVAILABLE`. Повторы с тем же UUID безопасны. Сервер не принимает фото без действующего административного запроса. Просмотр только через авторизованный endpoint с проверкой филиала, без публичных URL. Серверная копия также истекает через 35 дней от исходной съёмки, а не от загрузки.

Без сети запрос ожидает связи. При открытом приложении опрос примерно каждые 30 секунд, в фоне — WorkManager; Android может отложить выполнение. Ошибка передачи фото не отменяет уже принятые отметки. Удаление локальных фото выполняется фоновым заданием без требования сети; отключённое устройство очищается после запуска. События и SHA256 не удаляются вместе с фото.

Сетевые повторы: 408/425/429/5xx; 401/403 приостанавливают авторизованную отправку без удаления очереди. 404 сообщает об отсутствии интеграции. 400/409/413/422 сохраняют запись для проверки. Таймаут оставляет тот же UUID в очереди.

Поле `receipts` в state — массив подтверждений ранее отправленных событий данного устройства (та же структура, что ответ events). Он включает решения по REVIEW после проверки администратором; клиент проверяет eventId и привязку перед применением. Решения должны оставаться доступными до подтверждения получения устройством либо в течение всего согласованного периода хранения событий. Удалять решение раньше восстановления связи нельзя.

Клиент приостанавливает отправку зависимых отметок сотрудника, пока предшествующий приход/уход находится в REVIEW. Отметки других сотрудников продолжают отправляться. После получения решения через state зависимые события отправляются повторным проходом с прежними UUID. Локальные ошибки валидации, не принятые сервером, должны разбираться администратором отдельно; они никогда не означают начисленных часов.
