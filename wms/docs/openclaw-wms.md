# OpenClaw в нашей WMS

## Подготовленный результат на 28.09.2026

Ветка `feature/openclaw-wms-20260928` создана от текущей рабочей ветки
`fix/spirit-warm-payroll-compatible-20260928`, commit `a1d139c2`.
PR предназначен для `publish/feature/wb-print-check`. Проданная WMS/FFULHAB
не входит в этот выпуск. Новая интеграция включается только явным серверным флагом.

На нашем сервере установлены OpenClaw `2026.9.6` и отдельный Node.js `24.19.0`:
`/opt/wms-openclaw`. Системный Node и контейнеры WMS не заменены.
Служба `wms-openclaw` запущена отдельно от WMS для проверок модели и команд.
Подключение WMS остаётся выключенным до выпуска проверенного delta.
Её конфигурация проверена командой `openclaw config validate` установленной версии.
Файлы `gateway.env` и `provider.env` имеют права `0600`, владелец root.

По указанию Константина доступ к серверным действиям получают все реальные
администраторы (`system:admin`) и владельцы (`administrationEnabled`).
Демонстрационные, клиентские и ограниченные клиентской областью аккаунты
не допускаются даже при ошибочно назначенных широких правах.
Для другого состава доступа предусмотрен режим allowlist по ID пользователей.

## Что меняется

- `WmsOpenClawService.submit/get/status`: проверка прав на сервере, стабильные
  сеансы по userId + склад + conversationId, постоянная запись задания в AuditLog.
- Первичный ключ `openclaw:<requestId>` защищает от повторной отправки, включая
  одновременные запросы в разные процессы API. Другой пользователь не получает
  результат чужого задания. Идентификатор нельзя использовать с другим содержимым.
- После переключения прежние chat/knowledge и административный планировщик
  блокируются на API. Выгрузка разрешённых складских таблиц остаётся отдельным
  инструментом. Два входа в ИИ в веб-интерфейсе открывают один OpenClaw-чат.
- Веб-клиент сохраняет идентификатор задания до POST. После обновления страницы
  читает состояние через GET, не отправляя команду повторно.
- Таймаут, разрыв связи или потерянный результат означают UNKNOWN. Агент мог
  выполнить изменения; автоматического повторения нет. Оператор должен проверить
  журнал и факт изменений. Историческое RUNNING старше 11 минут также показывается
  как UNKNOWN без перезапуска операции.

Транспортный журнал WMS сохраняет запрос, пользователя и итог. Детальные вызовы
инструментов и команды хранятся в состоянии OpenClaw; это не подтверждение
правильности изменений — агент обязан проверить фактический результат операции.
Один привилегированный gateway предназначен для доверенных администраторов
одной нашей WMS, а не для изоляции недоверенных арендаторов.

### Альтернативный режим — OpenAI API

Конфигурация: `infra/openclaw/`. Installer добавляет отдельного Linux-пользователя
`wms-openclaw` с доступом к Docker. Это намеренно даёт возможность обслуживания
нашего сервера. Внешний Control UI отключён, gateway слушает адрес Docker-моста
`172.18.0.1:18789`, не публичный интерфейс.

Ключ OpenAI вводится скрыто в терминале сервера:

```bash
sudo /opt/wms-openclaw/configure-openai.sh
```

Не передавать ключ в чат, Git, командную строку или журнал. Скрипт только сохраняет
ключ; не запускает службы. Gateway-токен создан локально криптографическим
генератором, его значение не нужно показывать пользователю.

После проверки доступа к выбранной модели и запуска gateway
в API нашей WMS добавляются:

```dotenv
WMS_OPENCLAW_ENABLED=true
WMS_OPENCLAW_ACCESS=administrators
WMS_OPENCLAW_URL=http://172.18.0.1:18789
# WMS_OPENCLAW_TOKEN загружается из защищённого gateway.env, не хранится в Git.
```

Для allowlist вместо режима administrators задать `WMS_OPENCLAW_USER_IDS`.
Ключ OpenAI нужен только gateway, браузер получает лишь токен сессии WMS.
Нельзя публиковать gateway за внешним reverse proxy или отдавать его токен клиенту.

До включения WMS: проверка конфигурации, привязки сети, закрытия неавторизованного
запроса, реальный ответ модели, безопасное тестовое действие в рабочем каталоге,
проверка отказа обычному сотруднику/клиенту и повторного запроса задания.

## Выпуск и откат

**Не выкладывать полную локальную сборку поверх production.** Текущая база имеет
`sourceParityVerified=false`. Перед выпуском повторно сверить живые образы:

- API при подготовке: `edaec90e3b3b9e777c0dc9d4f3083a4ad9fe60036a454c6e0022f016b629797b`.
- Web при подготовке: `c958929305d4139a6f884cd2f6742a598c2cb307701d36a613aef01505e7a04e`.

Исходники wms-ai service/controller/module совпали с работающим сервером после
нормализации переводов строк. AdministrationService на сервере новее — его этот
PR не меняет. До выпуска отдельно сверить свежие AdministrationController,
AdministrationInternalApiService и затронутые файлы web; сохранить текущий runtime
и применять только проверенный delta согласно `release-workflow.md`.

Откат интеграции: вернуть сохранённые образы API/web и прежнюю конфигурацию API,
остановить gateway. Выключение флага возвращает старый ИИ. Это не отменяет уже
выполненные агентом операции; их откат проводится отдельно по журналу и снимкам.
